# 乐观锁 vs 悲观锁：冲突重试税与排队税的对照实验

对应文章：`content/posts/optimistic-vs-pessimistic-lock.md`。

把"读多写少用乐观锁"这句没量化的话拆成两笔税：
**乐观锁交重试税**（每次尝试以冲突率 `p` 失败，期望重试 `p/(1-p)` 次），
**悲观锁交排队税**（N 个并发事务同时争同一行时，FIFO 平均等待 `(N-1)/2 × 持锁时间`）。
两者有交叉点，取决于冲突率、并发度与成本比。本实验用 Go 把两条曲线画出来。

## 运行

```bash
go run .                      # mode=sweep: 受控冲突率对照 + 交叉点曲线
go run . -mode storm          # mode=storm: 热行秒杀, 乐观锁重试风暴
go run . -a 100 -s 200        # 改乐观单次尝试/悲观持锁成本(µs)
go run . -mode storm -gap 100us -k 128 -runs 5
```

| flag | 默认 | 说明 |
| :--- | :--- | :--- |
| `-mode` | `sweep` | `sweep`(冲突率受控对照) / `storm`(热行事件交错) |
| `-a` | 100µs | 乐观锁单次尝试成本(读版本 + 条件更新) |
| `-s` | 200µs | 悲观锁持锁服务时间(读 + 更新 + 提交) |
| `-samples` | 200000 | sweep 公式验证的独立抽样次数 |
| `-gap` | 200µs | storm 的读→写窗口 / 悲观持锁时间 |
| `-k` | 128 | storm 最大并发度(从 2 翻倍到 k) |
| `-runs` | 5 | storm 重复轮数(取最优 wall) |

## 输出

- `sweep`：公式验证表（测得均值 vs 理论 `1/(1-p)`）+ 并发网格（`p × N`，标记乐观/悲观胜者）+ `sweep.csv` + `crossover_N20.svg` / `crossover_N100.svg`（固定 N 的"冲突率曲线"，标交叉点 `p*`）。
- `storm`：热行对照表（乐观总尝试次数/重试放大 vs 悲观）+ `storm.csv` + `storm.svg`。

## 口径（诚实边界）

- 所有延迟是**模拟成本单位**，`a`/`s` 是我设定的比例，不是真实 MySQL 延迟。真实延迟需对 DB 压测后回填正文【本机实测待补】。
- sweep 的随机部分是乐观锁的几何分布尝试（每次尝试以概率 `p` 独立失败）；悲观部分是确定性 FIFO 队列（N 并发同时到达，平均延迟 `(N+1)/2 × s`）。这是受控对照：同一行格子只改一个变量（冲突率或并发度）。
- 交叉点公式：`p* = 1 - 2a / (s(N+1))`。`a=100`、`s=200` 时 `N=20 → p*≈0.952`，`N=100 → p*≈0.990`：并发度越高，悲观排队税越贵，乐观锁的适用范围反而越宽。**注意这与"读多写少用乐观锁"无关，它只由冲突率驱动**。
- storm 是真实 goroutine + `sync/atomic` CAS 的事件交错：一次成功提交使所有在途读者版本失效，重试者又彼此碰撞，总尝试次数随并发度放大（`K=128` 时约 `64×`）。悲观（互斥锁）总尝试次数恒等于 K，无浪费。`wall` 接近是因为进程内 CAS 便宜；真实 DB 里每次尝试是一次网络往返，`64×` 尝试会变成 `64×` 的库上负载。
