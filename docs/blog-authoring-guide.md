# 技术博客写作与重构指南

本指南只服务于 `content/posts/` 下的技术文章写作、审核与重构。它不保存发布批次、草稿数量或当前质量债；这些可变状态分别由 `review.md` 和 `docs/topic-backlog.md` 管理。

目标不是让文章更像固定模板，而是让资深工程师读完后能回答三个问题：

1. 这个机制真正承诺了什么，不承诺什么？
2. 它为什么这样设计，代价被移到了哪里？
3. 我怎样用代码、实验或一手资料验证，而不是只记住结论？

## 一、动笔前先填写“文章任务卡”

任务卡是工作笔记，不必原样进入正文。新写、重写和深度审核都先回答：

| 字段 | 必须回答的问题 |
| --- | --- |
| 目标读者 | 他已经知道什么，最容易在哪一步误判？ |
| 核心问题 | 读者读完后必须能独立解释或决定什么？ |
| 知识主角 | 标题里真正要讲透的机制、合同或决策是什么？ |
| 熟悉入口 | 用哪种语言、API、事故或现象帮助读者进入主题？ |
| 核心判断 | 能否用 2–3 句给出结论、条件与边界？ |
| 因果主线 | 从入口到结果，中间有哪些状态变化、所有权转移或失败分支？ |
| 证据 | 哪些来自一手资料，哪些来自本地实验，哪些仍无证据？ |
| 取舍 | 没选什么，代价是什么，在哪些工作负载下结论会反转？ |
| 时效性 | 哪些版本、默认值、价格、协议或运行时行为需要按当前日期核对？ |
| 下一步 | 读者能运行什么、观测什么，或继续研究哪组可证伪问题？ |

如果任务卡无法确定“知识主角”，不要急着扩写。先删掉互相竞争的主题，直到标题、TL;DR 和主要篇幅回答同一个问题。

## 二、用一条因果主线组织深度，而不是罗列知识点

清晰不等于短。真正需要压缩的是并行主线，不是机制深度。

### 1. 尽早给出完整路径

正文前四分之一内，读者应看到一条可以反复回看的总路径，例如：

```text
公开 API
  → 第一次真实操作
  → 边界返回值或状态
  → 进入等待/重试/恢复
  → 中间层保存状态
  → 底层事件发生
  → 唤醒或完成
  → 重试并返回调用者
```

后续章节逐段放大这条路径，不要在主线出现前先塞入完整术语表、历史年表和所有 API 参数。

### 2. 找到“被省略的中间层”

浅文章常见问题不是没有底层名词，而是跳过了真正连接因果的那一层。

审核时追问：

- 线程或任务到底睡在哪里？
- 谁保存等待关系、重试状态、buffer 所有权或代数？
- 状态变化后谁负责唤醒，怎样避免丢事件？
- close、timeout、取消和复用怎样与正常路径竞争？
- 用户看到的阻塞 API 与底层非阻塞机制之间由谁翻译？

如果文章从公开 API 直接跳到“内核很快”“runtime 会处理”“框架自动重试”，应继续向下追一层，直到责任主体和状态转移明确。

### 3. 每个章节只推进一个读者问题

信息型标题应当能连成推理链。检查相邻章节：

- 本节回答了什么新问题？
- 它依赖上一节的哪个结论？
- 删除本节后，因果链会断，还是只少一组旁支知识？

只提供术语百科、但不改变主线理解的内容，应压缩成表格、移入附录或删除。

## 三、熟悉技术只是入口，不能抢走知识主角

用 Go、TypeScript、某个框架或一次事故作为入口时，先明确它的角色：

- **入口**：帮助读者从熟悉代码提出问题。
- **映射**：在核心机制讲清后，回到语言/runtime 看它如何消费该机制。
- **主角**：只有文章本来就在讲该语言/runtime 时，才占据主要篇幅。

重构时检查篇幅：如果标题承诺 Linux I/O 多路复用，但大部分正文在解释 Go 调度器，说明入口已经劫持主题。

### 标题中的箭头必须诚实

“从 A 追到 B、C、D”可能表达两种完全不同的关系：

1. 真实调用链：A 确实依次调用 B、C、D。
2. 演进或对照链：B、C、D 是解决同一问题的不同方案。

正文开头必须说明属于哪一种。不能为了标题顺滑，把比较关系写成不存在的顺序调用栈。

### 从本次 I/O 文章提炼出的例子

- 熟悉入口：Go `conn.Read`。
- 知识主角：`select` / `poll` / `epoll` 的 readiness 与等待模型。
- 隐藏中间层：文件对象 `poll` 回调与 wait queue。
- 需要澄清：Go 在 Linux 上直接使用 epoll，不会依次调用三套 API。
- 回到入口：最后只用一节解释 `EAGAIN → waitRead → runnable → retry`。

这个例子用于说明“入口与主角如何分工”，不是要求其他文章复制同样的章节数量。

## 四、先定义合同，再讲实现和性能

读者在看源码或数据结构前，先要知道接口合同：

- 返回的是 readiness、completion、ack，还是仅仅“请求已接收”？
- 成功意味着本地写入、持久化、复制完成，还是业务最终生效？
- timeout 取消了等待、底层操作，还是两者都没有？
- 一次通知对应完整消息、部分数据，还是多个消息？
- 顺序、幂等、原子性和可见性在哪个边界成立？

定义合同至少包含三部分：

1. **保证什么**。
2. **不保证什么**。
3. **调用者仍需负责什么**。

只有合同明确，后面的实现对比才不会沦为函数签名或组件清单。

## 五、横向比较必须使用同一条比较轴

比较多个方案时，先冻结维度，再逐项填充。不要每个方案各讲一套优点。

常用维度：

| 维度 | 追问 |
| --- | --- |
| 状态保存 | interest、buffer、offset、重试次数或事务状态存在哪里？ |
| 注册生命周期 | 每次调用重建，还是跨多轮持久存在？ |
| 交付结果 | 返回候选集合、ready 子集，还是实际完成结果？ |
| 所有权 | 谁拥有请求、buffer、取消权和最终清理责任？ |
| 热路径成本 | 成本随总规模、活跃子集、变化量还是争用增长？ |
| 失败语义 | timeout、close、重试、部分成功和重复通知怎样处理？ |
| 适用边界 | 在什么负载、部署和团队能力下结论会反转？ |

性能文章不要只写“`O(1)`”“更快”“吞吐更高”。先给变量命名，例如：

- `N`：长期对象总数。
- `K`：当前活跃或 ready 子集。
- `Δ`：两轮之间的新增、删除或修改量。
- `C`：争用、并发 worker 或共享资源程度。
- `F`：故障、重试或取消比例。

变量名称按主题调整，但必须解释性能结论依赖什么，而不是把一个本机点值外推成普遍规律。

## 六、深度文章至少经过七层追问

不要求每篇都使用七个章节，但论证应覆盖与主题相关的层次：

1. **现象**：读者实际看到什么？
2. **合同**：系统保证和不保证什么？
3. **机制**：状态怎样流动，谁等待、谁唤醒？
4. **数据结构或所有权**：状态具体保存在哪里？
5. **反例**：哪种部分成功、并发或边界条件会打破直觉？
6. **成本模型**：规模、活跃比例、变化量和争用怎样影响结果？
7. **证据与边界**：源码、实验和生产证据分别证明到哪里？
8. **演进与下一步**：新扩展改了参数、优化路径，还是改变合同？

层数不是文章目录模板。事故文可以用时间线承载这些问题，原理文可以按设计追问，选型文可以用比较矩阵。

## 七、按文型选择叙事，不批量复制结构

| 文型 | 推荐主线 | 必须避免 |
| --- | --- | --- |
| 事故、恢复、故障边界 | 时间线 → 证据 → 失效不变量 → 修复与未解风险 | 只讲最终根因，没有错误线索和恢复过程 |
| 底层原理、运行时机制 | 现象 → 合同 → 因果路径 → 数据结构 → 反例 | 术语百科、源码函数逐个点名 |
| 方案比较、技术选型 | 使用场景 → 同维度比较 → 反例 → 决策边界 | 功能清单、所有方案都“适合不同场景” |
| 工具链、工程实现 | 目标 → 可运行路径 → 关键取舍 → 失败尝试 → 验证 | 只给最终配置，不解释为什么 |
| 观点澄清、反直觉判断 | 明确论点 → 最强反例 → 机制解释 → 成立条件 | 口号先行、没有可证伪边界 |
| 系列续篇 | 上一篇未回答的问题 → 新机制 → 跨篇承诺闭合 | 重复前文背景、制造不存在的后续钩子 |

需要历史样本时，按文型最多选一个主样本；确有跨篇合同再读一个相邻文：

| 文型 | 候选主样本 | 学习点 |
| --- | --- | --- |
| 事故、恢复 | `content/posts/wal-crash-recovery.md` | 失败时序、恢复不变量、证据闭环 |
| 工具链、建站 | `content/posts/building-a-markdown-blog.md` | 从问题到工件与验证 |
| 观点澄清 | `content/posts/ai-backend-no-magic.md` | 论点、反例和成立边界 |
| 横向比较 | `content/posts/js-ecosystem-layers.md` | 统一维度、语义差异与取舍 |

样本只学习质量和责任边界，不复制句式、隐喻和章节节奏。

## 八、实验必须同时写“证明什么”和“不证明什么”

每个本地实验都建立最小证据卡：

| 字段 | 内容 |
| --- | --- |
| 问题 | 实验只回答哪一个问题？ |
| 环境 | 机器、OS、runtime、依赖锁、关键配置 |
| 输入 | 规模、并发、持续时间、预热和重复次数 |
| 控制变量 | 对照组之间唯一改变了什么？ |
| 原始输出 | 可定位的 evidence 路径 |
| 派生 | 公式、分母、单位和舍入方法 |
| 支持结论 | 这组结果直接支持什么？ |
| 不支持结论 | 不能外推到哪些平台、生产负载或语义？ |

常见越界：

- goroutine 数量不能单独证明 OS 线程数量。
- 看到某个 syscall 不能解释完整业务延迟。
- loopback 结果不能代表公网或跨地域网络。
- 顺序调用通过不能证明并发幂等。
- in-process 请求不能称为网络 API p99。
- 模拟器可以验证模型方向，不能自动证明真实内核或生产容量。
- 根 `npm test` / `npm run build` 不能证明被排除的 `experiments/` 正确。

完整代码块必须来自验证过的工件。为教学省略的内容标明“伪代码”或“节选”，并明确省略了什么。

## 九、写“近年变化”时分清四种演进

不要把所有新 API 都写成“下一代替代品”。按下面四类调查：

1. **同一合同的表达扩展**：例如 timeout 精度、signal mask、更多 flag。
2. **同一模型的热路径优化**：例如 busy polling、批处理、减少唤醒。
3. **新的应用对象**：原有等待模型开始观察 timer、process、signal 或其他 fd。
4. **交付合同改变**：从 readiness 变成 completion，或出现两者混合迁移。

每项都回答：

- 引入版本和核对日期是什么？
- 改变了参数、实现路径还是语义合同？
- 谁承担新增的 buffer、取消、队列和生命周期复杂度？
- 旧方案为什么没有消失？
- 当前语言 runtime 或框架是否真的采用，还是只存在内核能力？

优先使用官方文档、规范、源码、RFC 或论文。社区文章可以提供问题线索，不能独立支撑版本和默认行为。

## 十、把下一步写成可执行研究问题

结尾不要只写“未来可以继续研究”。给出 3–5 个可验证问题，每个包含：

- 假设或争议点。
- 控制变量。
- 观测指标。
- 故障或反例。
- done criterion。
- 结果不能外推到哪里。

好的研究问题示例形状：

> 固定总连接数，分别改变 ready 比例和连接 churn，测量等待调用、控制调用、CPU、context switch 与 p99，判断结构优势由总规模还是活跃子集主导。

它比“后续对比几种方案的性能”更容易执行，也更不容易得到无意义结论。

## 十一、编辑层面保持清晰，但不要削平作者声音

- 用户要求标题方案时，一次给出推荐标题和 1–2 个备选；每个标题用一句话说明它承诺读者获得哪层认知。锐度来自具体机制、反直觉判断或可验证结构，不来自夸张。
- 同批文章检查标题、章节节奏和隐喻密度，避免多篇重复“账本、税、三档、裁判”等同一种表达装置。
- 开头两三句直接给问题或判断，不写通用背景和“本文将介绍”。
- 一个段落只推进一个观点；出现转折时优先换段。
- 小标题表达判断，不使用裸“背景、架构、结果、总结”。
- 表格承载同字段对比，图承载三方以上关系、状态变化或调用路径。
- 代码之后解释关键状态和 why，不逐行复述 what。
- 禁止口号式警句、三连短句、排比广告语和“显而易见/就是这么简单”。
- 幽默只服务于理解，不用来替代证据。
- 结尾回到开头的问题，给出读者可以执行的判断或实验。
- 文章可以长，但每一节必须推进同一知识主线；不能用删掉机制细节伪装简洁。

## 十二、重构旧稿时使用这张审核卡

先不改字句，完成结构诊断：

1. 标题承诺的知识主角是什么？
2. 主线第一次完整出现在哪一节？是否太晚？
3. 哪些章节正在争夺文章中心？
4. 熟悉语言或框架是入口、映射，还是已经劫持主题？
5. 是否把对照关系误写成顺序调用链？
6. 哪个隐藏中间层没有解释，导致上下两层只靠“自动处理”连接？
7. 文章先定义了合同，还是先罗列函数和组件？
8. 横向比较是否使用同一维度？
9. 性能结论是否声明总规模、活跃比例、变化量与争用？
10. 每个关键机制是否有一个能让它失败的反例？
11. 实验是否明确“不证明什么”？
12. 近年变化是参数扩展、热路径优化、新应用，还是合同改变？
13. 哪些段落能移到表格、附录或参考资料，而不破坏因果链？
14. 读者读完能继续运行什么、观测什么、研究什么？

然后再重写：

- 先写新的标题、description、TL;DR 和章节问题链。
- 再移动、删除或合并旧段落。
- 最后补缺失机制与证据。
- 不要沿旧稿顺序逐段润色，否则散乱结构会被原样保留。

## 十三、交付前自检

### 聚焦

- [ ] 标题、TL;DR、主要篇幅和结论回答同一个核心问题。
- [ ] 熟悉入口没有抢走知识主角。
- [ ] 开头澄清了真实调用链与演进/类比关系。

### 深度

- [ ] 合同、机制、状态保存、唤醒/完成和失败路径可以连成因果链。
- [ ] 至少解释一个隐藏中间层，而不是只列上下层组件。
- [ ] 关键判断包含条件、取舍和反例。
- [ ] 性能讨论声明了影响结果的变量。

### 证据

- [ ] 时效性事实写明核对日期并引用一手资料。
- [ ] 完整代码已运行；伪代码和节选已标注。
- [ ] 实验环境、命令、输入、原始输出和公式可复现。
- [ ] 正文同时说明实验支持与不支持的结论。
- [ ] 标题、TL;DR、正文、表格和结论中的数字同源。
- [ ] 共享同一实验的跨篇数字、单位和样本日期保持一致。

### 表达

- [ ] 章节编号连续，标题是信息型判断。
- [ ] 每段只推进一个观点，没有草稿批注、乱码、占位和死链。
- [ ] 图、表、代码都有明确解释，不是装饰。
- [ ] 没有批量模板节奏、重复隐喻和 AI 腔。
- [ ] 结尾给出具体判断、操作或可验证研究问题。
