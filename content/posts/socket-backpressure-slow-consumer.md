**TL;DR：** 网络服务的"慢消费者"问题有一个被低估的真相：**缓冲区没满之前，一切正常；缓冲区一满，背压（backpressure）就开始逐跳传导**——接收方不读 → 接收缓冲满 → TCP 窗口归零 → 发送方内核停止发送 → 发送缓冲堆满 → `send()` 返回 EAGAIN 或阻塞 → 应用线程被钉住 → 连接占满 → 上游也开始堆积。整条链路像一个连在一起的水管，**压力从最慢的一环出发，往上游一截一截传**。诊断的关键不是看谁"慢"，而是用 `ss` 看每一跳的缓冲区水位——谁的水位满了，谁就是背压的源头。

## 一、先讲清楚：背压为什么必须存在

背压不是 bug，是系统的**自我保护机制**。没有缓冲区的两端直连，发送方每写一个字节都要等接收方消费完——那就是"逐字节同步"，吞吐为零。缓冲区存在的意义就是**解耦速度差**：快的一端可以多写一点，慢的一端慢慢消化。

问题出在缓冲区是**有界的**：

1. **接收缓冲**（`SO_RCVBUF`，默认约 128KB–256KB）——接收方内核从网卡取数据放这里，应用不读就一直堆。
2. **TCP 接收窗口**（`rwnd`）——接收缓冲剩余空间的"声明"，通过 TCP 头里的 window 字段告诉对端"你还能发多少"。**缓冲一满，窗口归零，对端必须停发**。
3. **发送缓冲**（`SO_SNDBUF`）——发送方内核放"已发未确认"和"待发"数据。窗口为零时，这里会堆满。
4. **应用层**——`send()` 在发送缓冲满时返回 EAGAIN（非阻塞）或阻塞（阻塞模式）。

于是背压的传导链完整了：

```mermaid
flowchart LR
    A["上游服务<br/>(发送方)"] -->|"send() 阻塞/EAGAIN"| B["发送缓冲满<br/>SO_SNDBUF"]
    B -->|"TCP window = 0<br/>对端停发"| C["接收缓冲满<br/>SO_RCVBUF"]
    C -->|"应用不读"| D["慢消费者<br/>(接收方应用)"]
```

**关键认知**：背压不会凭空消失，它只会**换位置**。要么消费方读得够快，要么缓冲堆满，要么……内存被打爆。所谓 OOM，"一半是内存不够，一半是缓冲区没人排队"——一条连接堆 256KB，一万条慢连接就是 2.5GB 的隐形内存。

## 二、用 ss 找到背压源头

排查背压不靠猜，靠看每一跳的水位：

```bash
# 看所有 ESTABLISHED 连接的缓冲区水位
ss -m -t state established

# 输出示例（重点看这三列）
# Send-Q: 发送缓冲待发字节数（接近 Send-Buffer 上限 = 发送方被堵）
# Recv-Q: 接收缓冲未读字节数（接近 Recv-Buffer 上限 = 消费方没在读）
# Busy:   最近窗口是否被占满
Recv-Q  Send-Q  Local Address   Peer Address
0       65536   :8080           :60000   <- 发送方堆满，上游在等
524288  0       :8080           :60001   <- 接收方堆满，这个连接在拖死你
```

判读规则只有两条：

1. **`Recv-Q` 接近 `Recv-Buffer` 上限** → 问题在本进程：应用线程没在读，或读太慢。先查代码，再查 GC 停顿。
2. **`Send-Q` 接近 `Send-Buffer` 上限** → 问题在**对端**：对方不读。这里要接着 `ss -m` 看对端的 `Recv-Q`——对端缓冲也满，说明链条往下传了。

```bash
# 想看对端的视角：连到对端机器上执行同样的命令
# 或者在本机看 TCP 窗口状态
ss -tin | grep -E "state established|wscale|rwin"
# rwin = 对端声明的接收窗口，如果长时间是 0（rwnd:0），背压就在这一跳坐实了
```

**窗口持续为零是背压的黄金证据**——它说明接收方已经对发送方说了"停"。`rwnd:0` 出现在哪一跳，源头就在哪一跳的下游。

## 三、慢消费者的典型形态

背压源头通常长成这几张脸：

| 形态 | 症状 | 排查入口 |
| :--- | :--- | :--- |
| 消费线程被 GC/阻塞占住 | Recv-Q 持续上升直到满 | GC 日志、线程 dump 看读循环是否停 |
| 消息处理是串行队列 | 队列长度增长，单条消息耗时飙高 | 队列深度指标（Redis/内存队列 size） |
| 下游 API 变慢 | 本服务 Recv-Q 满、Send-Q 满混合 | 全链路追踪（见[分布式追踪](/writing/distributed-tracing-otel)） |
| 死循环/线程饿死 | 单条连接永不消费 | 进程内每个连接的 Recv-Q 曲线 |

一个重要的"受害者"视角：**背压传导时，最先死的是最上游**。中间的服务只是堆缓冲，最上游的客户端在等响应超时，然后重试，把更多请求打进来——雪崩就是这么来的。所以做容量规划时，**慢消费者的容忍度不是"它自己的内存"，是"它往上传染到第几跳"**。

## 四、生产里三件该做的事

背压无法消灭（它是保护机制），但可以**设计出它的边界**：

1. **给消费者设明确的速率承诺**。任何"接收方"都要有可观测的消费速率（QPS + 单条耗时），慢的迹象在指标里先出现，而不是等到 Recv-Q 满。
2. **限流 + 背压要配合**。见[限流、熔断与降级](/writing/rate-limiting-circuit-breaker)：限流挡的是"进来的太多"，背压挡的是"出去的太慢"——一个是门，一个是闸，缺一不可。
3. **显式背压优于隐式缓冲**。能返回 503 让上游退避的，就别默默把请求堆在内存队列里。**队列是"把失败延后"的装置**：它没让请求成功，只让失败来得更晚、更集中。

## 结论：Recv-Q、Send-Q 和 rwnd 把慢消费者变成可观测水位

背压 = 缓冲区满之后，压力沿链路逐跳传导。查背压不猜性能，用 `ss -m` 量水位：**Recv-Q 满说明自己没在消费，Send-Q 满说明对端没在消费，rwnd:0 是最硬的证据**。工程上接受背压存在，但要把它的边界设计出来：消费速率可观测、限流与背压配合、用显式拒绝代替隐式队列。

下一步：在生产环境跑一次 `ss -m -t state established | sort -k4 -rn | head -20`，把 Recv-Q 最大的十条连接挑出来——看看它们对端的进程是什么。大概率你会第一次"看见"背压长什么样。
