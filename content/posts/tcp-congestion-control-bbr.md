**TL;DR：** TCP 的拥塞控制回答一个问题：在不制造拥堵的前提下，发送方最多能同时有多少数据在途？答案是一个窗口，叫 cwnd（拥塞窗口）。经典实现是"丢包驱动"：cwnd 指数爬到阈值、线性微调，一丢包就减半，形成锯齿；CUBIC 用三次曲线让大窗口链路爬升更快。BBR 换了个思路：不再等丢包，而是直接测量瓶颈链路的带宽与 RTT，把 cwnd 钉在 BDP（带宽 × 时延积）附近，吞吐不降、排队几乎为零。理解这三代算法，就能看懂云上带宽抖动、视频加载慢和"ping 很低但下载很慢"的怪现象。

## 一、 发送方的难题：不知道链路有多宽

两台机器之间有一个"管道"：出口带宽由路径上最窄的一段决定，叫**瓶颈链路**。发送方想知道瓶颈有多宽，但 TCP 是端到端的——中间的路由器不提供任何反馈，只有 ACK 能证明数据到了。于是 TCP 只能靠"试探"：多塞一点数据，直到出事。

出事有两种表现，对应两种不同的信号：

1. **丢包**：缓冲区溢出了。路由器收不下，直接丢弃。这是最古老的信号，经典拥塞控制只认它。
2. **延迟升高**：缓冲区还没满，但数据在排队。发送方看到 RTT 变大，说明管道已经被填到接近饱和——这是 BBR 一派的信号。

为什么不能无脑快速发？因为网络是共享的：所有流都挤在同一批路由器上。如果大家都不管不顾地猛发，路由器缓冲区被占满后开始丢包，所有流进入重传→重发→更堵的恶性循环，最终全网吞吐崩溃——这叫**拥塞崩溃（congestion collapse）**，是 1986 年促使 Van Jacobson 设计拥塞控制的历史事故。

所以 TCP 用**拥塞窗口（cwnd）** 限制在途数据量：发送方最多允许 `min(cwnd, rwnd)` 字节未确认（rwnd 是接收方通告的窗口，管"对方内存够不够"；cwnd 管"网络够不够"，两者共同约束）。cwnd 就是拥塞控制算法唯一要维护的状态。

```text
在途数据 = 已发送 - 已确认 ≤ min(cwnd, rwnd)
```

## 二、 慢启动与 AIMD：两根拐杖走天下

### 2.1 慢启动：指数探路

新连接不知道链路有多宽，最保守的做法是从一个很小的窗口（初始 10 个 MSS，约 14.6KB）开始，**每收到一个 ACK，cwnd 就加一个 MSS**。由于 ACK 是随窗口流水返回的，实际效果是每个 RTT 窗口翻倍——指数增长。

名字叫"慢启动"，实际是**最快的增长方式**：200ms RTT 的链路上，约 7 个 RTT 就能从 14KB 长到 1.8MB。它慢的地方在于起点低，不是斜率慢。指数增长不能一直持续，`ssthresh`（慢启动阈值）是刹车：超过阈值后进入拥塞避免，改指数为线性。

### 2.2 AIMD：加性增、乘性减

进入拥塞避免后，规则变为：**每个 RTT 只把 cwnd 加 1 个 MSS**（加性增），**一检测到丢包，cwnd 减半**（乘性减）。这就是 AIMD（Additive Increase Multiplicative Decrease）。

为什么是"加一减半"而不是别的比例？因为这是唯一能让多条流共享链路时收敛到公平的规则：谁的窗口大，谁的丢包概率高，减得越多，最终大家自动趋向均分带宽。这个性质叫**收敛性**，是 TCP 公平性的根基。

### 2.3 快重传与快恢复：别把一次丢包当成世界末日

最早的 TCP（Tahoe）一丢包就把 cwnd 打回 1，从慢启动重来——一次丢包前功尽弃。Reno 的改进是区分"丢包的严重程度"：

- **快重传**：收到 3 个重复 ACK 说明后续数据还在流动，只是中间丢了一段，触发重传而不是等超时（超时要等 1 个 RTO，通常 200ms 起步，太慢）。
- **快恢复**：判定为"轻度丢包"后，cwnd 只减半，然后从减半后的值线性爬升，不再回到慢启动。

超时（RTO）是最后的兜底：一连串重传都没收到 ACK，说明网络可能真的断了或严重拥塞，才把窗口打回 1。区分重传与超时，是判断网络状态的第一手经验：**丢包但 RTT 正常，多半是随机丢包；丢包且 RTT 飙升，多半是拥塞；大量超时，多半是路径故障**。

## 三、 CUBIC：把线性爬升换成三次曲线

Reno 的线性爬升在"高带宽高延迟"链路（即 BDP 很大的长肥网络）上有个致命问题：假设链路容量 10Gbps、RTT 100ms，BDP 是 125MB；丢包后 cwnd 减半到 62.5MB，Reno 要花 62.5MB / 1MSS ≈ 41000 个 RTT（约 68 分钟）才能爬回来。在这期间带宽白白浪费。

CUBIC 的解法：让 cwnd 沿**三次函数** 曲线增长，而不是直线：

```text
cwnd(t) = C × (t - K)³ + Wmax
```

其中 `Wmax` 是上次丢包时的窗口值。三次函数的特点：离开 Wmax 远的地方增长极快（快速恢复吞吐），接近 Wmax 时增长放缓（避免再次撞到丢包点），越过 Wmax 后再次加速探索（寻找更高容量）。配合 `tcp_cubic` 的 HyStart 等优化，CUBIC 成为 Linux 默认拥塞控制十余年的原因就是实测简单可靠：对绝大多数路径，它比 Reno 快，且不失公平。

但 CUBIC 依然是**丢包驱动** 的——它把丢包当作拥塞的证明。这个前提在高速链路上越来越不成立：现代链路 0.01% 的随机丢包率（比如无线、丢包率为正的跨洋线路）就足以让丢包驱动的算法把 cwnd 永远压在低档，因为每次撞到"随机丢包"都被当成拥塞减半。

## 四、 BBR：用模型代替丢包信号

Google 在 2016 年发布 BBR，换掉了整个推理链条：**不再用丢包当拥塞信号，而是直接测量链路模型的两个参数**：

- **max_bw（最大带宽）**：单位时间确认的字节数峰值，用窗口最大值过滤掉噪声。
- **min_rtt（最小时延）**：链路上所有 RTT 中的最小值，代表"管道空"时的真实传播时延。

这两个值相乘就是 **BDP = 带宽 × 时延积**：链路能同时容纳的在途数据上限。BBR 的思路是让在途数据量恰好等于 BDP——既不多（不多排一分队），也不少（不少浪费一毫带宽）。

![丢包驱动与 BBR 的拥塞窗口曲线对比：前者锯齿爬升，后者在 BDP 附近平稳巡航](/images/congestion-window-curve.svg)

*图注：丢包驱动的窗口是"涨到丢包→减半"的锯齿；BBR 测得 BDP 后直接巡航在其附近，不靠丢包信号。*

BBR 用四个相位交替逼近这个点：

1. **Startup**：像慢启动一样指数增长，但**不是靠丢包停止**，而是当"带宽增长放缓超过 25%"时判定已接近链路容量，提前收手——不等缓冲区填满。
2. **Drain**：把 Startup 阶段排进队列的多余数据排空，让 RTT 回到 min_rtt 附近。
3. **ProbeBW**：稳态阶段，以 8 个 RTT 为周期，8 周期中有 7 个按 `pacing_gain = 1.0` 精确限速发送（pacing 是 BBR 的另一个武器：把突发数据平滑成均匀速率），1 个周期用 `1.25` 的增益试探更高带宽、用 `0.75` 的增益排空缓冲。
4. **ProbeRTT**：周期性把发送压到最低，持续一个 min_rtt，刷新对链路最小 RTT 的估计（避免被长期排队污染）。

结果是在 Google 实测里，BBR 在跨洋链路（高丢包、高 BDP）上把吞吐提升了 2~25 倍，同时把排队延迟从几十毫秒压到接近零。YouTube 全面启用 BBR 后，播放缓冲大幅下降，同时没有影响其他流的公平性。

## 五、 实践：看懂你的网络为什么慢

拥塞控制是内核里默认在跑的东西，你不需要改它，但读懂现象需要它：

**1. "带宽时高时低"是锯齿的投影。** 丢包驱动的连接（Reno/CUBIC 的小流）天然是锯齿形的：丢包减半→爬升→再丢包。云上按带宽计费的下载任务忽快忽慢，多半就是这个。`ss -i` 能直接看到当前 cwnd 与 rtt：

```bash
$ ss -i 'dport = :443'
State   Recv-Q Send-Q  Local Address:Port  Peer Address:Port  Process
ESTAB   0      0       10.0.0.2:52310     203.0.113.7:443    cubic wscale:7,rto:220,rtt:42.3/22.5 ato:40 mss:1448 cwnd:32
```

`cubic` 是当前算法，`cwnd:32` 表示当前窗口 32 个 MSS。若 cwnd 长期不涨，大概率在持续丢包。

**2. "ping 很低但下载很慢"= 小流吃大亏。** 下载任务只有几个连接时，慢启动的指数增长会被 RTT 限制，首屏之前窗口还没爬上去；而 RTT 低的连接瞬间就把窗口顶满。跨洋访问时把连接数×4 或开启 HTTP/3（多流）都比调内核参数有效。

**3. bufferbloat：路由器缓存太厚不是好事。** 大缓冲区本来防丢包，但丢包驱动的算法会一直填到缓冲区满才减半——于是你的包在路由器里排队 200ms 才被转发，RTT 虚高。症状是"下载的时候游戏延迟飙升"。这就是为什么 BBR 这类基于 RTT 的算法有意义，也是 `fq` 队列规则（公平排队 + 逐流限速）在家庭路由器上口碑爆棚的原因。

**4. 改算法的姿势。** Linux 上用 `sysctl net.ipv4.tcp_congestion_control=bbr`（内核 4.9+）或 per-socket 的 `TCP_CONGESTION` 选项切换。对大多数公网服务，CUBIC 依然是最稳的默认值；BDP 大、随机丢包率高的链路（跨洋、卫星、5G 边缘）才是 BBR 的主场；内网 RTT 极低的链路两者差别不大。别在生产环境一股脑全换——先在一个区域灰度，对比 P95 吞吐与 RTT 再决定[^1]。

[^1]: 延伸阅读：Van Jacobson 1988 年论文《Congestion Avoidance and Control》是全部现代拥塞控制的地基；Google 的 BBR 论文（ACM Queue 2016）给出了四个相位的完整伪代码；`ss -i` 与 `tc` 是观察 cwnd 与队列的两个利器。
