**TL;DR：** B+Tree 的写放大不在“分裂那一瞬间多写了一两页”，而在分裂策略长期决定的**叶填充率**：本仓库的固定 seed 教学模型中，16KB 页、128B 行、20 万行时，顺序插入叶填充率为 99.968%，总页数为 1581；随机插入叶填充率为 69.661%，总页数为 2268，多 43.5%。这些数字只说明该模型里的页分裂与空间结果，不是 InnoDB 的磁盘、redo 或 fsync benchmark。

## 一、先纠正直觉：把「写放大 = 分裂次数 × 分裂成本」当唯一模型会失真

"B+Tree 写放大来自页分裂"——这句话半对半错。错在把"分裂"当成预算的唯一来源。实际账本分两层：

1. **分裂的瞬时成本**：一次叶分裂 = 1 个新页 + 父指针更新，所谓"写放大 2-3"说的是这一个瞬间的页写入量；
2. **分裂的长期成本**：分裂在页的中部切开（随机主键场景），旧页的一半空间永远空着 → 叶填充率从 ~100% 掉到 ~68%。

本篇模型只量化叶页分裂、叶页填充率和一个简化的内部页数量估算，不把“页数多 43.5%”直接等同于写放大。后者要进一步知道 buffer pool 命中、脏页淘汰、redo/undo、检查点、刷盘和文件系统行为。可保留的判断是：在相同行大小和页大小下，随机中间分裂会让更多叶页长期处于半满状态，空间与缓存占用因此变差。

## 二、模拟实验：顺序 vs 随机主键，页大小三档

模拟器在 `experiments/btree-page-split/sim.py`。它把每行简化为固定 128B，只模拟叶页：顺序插入追加到最右页，随机插入选择已有叶页并在中点分裂。内部页数量按叶页数和 `3/4` 容量做估算，目的是观察趋势，不是复刻 InnoDB 的页目录、记录格式或分裂策略。默认输入为 20 万行，seed 为 `20260817`。

| 页大小 | 每页行数 | 顺序叶填充 | 顺序总页数 | 随机叶填充 | 随机总页数 | 随机/顺序总页数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 4KB | 32 | 100.000% | 6523 | 70.091% | 9306 | 1.427x |
| 8KB | 64 | 100.000% | 3194 | 69.568% | 4589 | 1.437x |
| 16KB | 128 | 99.968% | 1581 | 69.661% | 2268 | 1.435x |

三个页档都指向同一方向：在这个模型和 seed 下，随机插入总页数约为顺序插入的 `1.427–1.437` 倍。这里的“总页数”包含按简化规则估出的内部页，不能拿来直接推断某个数据库的物理文件大小；它只能支持“页越大，单页容纳行数增加，但随机中间分裂仍会留下大量空闲空间”这一层判断。

**为什么顺序主键更容易保持高填充？——append 路径**。当新键永远大于现有所有键时，模型只在最右侧追加；随机键会把插入压力分散到已有叶页，叶页在中间位置分裂后，两边需要等待后续插入才能重新填满。因此，顺序与随机的差异首先是插入位置分布的差异，不是“顺序键天然没有分裂”。

## 三、把账算穿：分裂、填充率、页数与写放大边界

页大小 16KB、行 128B 时，一页最多容纳 128 行。对固定 seed `20260817` 的模型输出，先把叶页和估算的内部页分开看：

| 指标 | 顺序 | 随机 |
| --- | ---: | ---: |
| 叶填充率 | 99.968% | 69.661% |
| 叶页数（20 万行） | 1563 | 2243 |
| 总页数（含估算内部页） | 1581 | 2268 |
| 叶分裂次数 | 1562 | 2242 |
| 随机相对总页数 | — | **+43.5%** |

这张表可以支持一个空间层面的推论：相同数据量下，随机模型要维护更多的叶页和内部页，缓存所需页数也更多。它不能单独支持“磁盘写量同步增加 43%”，因为实际写入还取决于脏页是否重复修改、buffer pool 淘汰、redo/undo、checkpoint、doublewrite、fsync 以及文件系统；本篇没有模拟这些机制。

在这个无删除、无更新的叶页模型里，叶页数等于叶分裂次数加一；内部页不是逐次分裂的实现结果，而是按叶页数估算的汇总值。因此不能把 `2242` 次叶分裂直接解释成“2242 次整棵树的物理写放大”。

## 四、页大小怎么选：4KB 也救不了随机键

页大小三档的对照说明**页小的填充率并没有更好**（本模型的随机插入都在约 70%）。页大小改变的是分裂频率的结构：

| 页大小 | 每页行数 | 随机叶分裂次数 | 叶分裂率（每行） |
| --- | ---: | ---: | ---: |
| 4KB | 32 | 8916 | 约 1/22.4 |
| 8KB | 64 | 4491 | 约 1/44.5 |
| 16KB | 128 | 2242 | 约 1/89.2 |

页越小，叶分裂越频繁（4KB 为 8916 次，16KB 为 2242 次），而随机叶填充率仍落在约 69.6%–70.1%。这说明增大页可以降低“每行摊到的叶分裂次数”，但不能从模型中推出它消除了随机插入导致的空间空洞；内部页在这里仍只是估算值。

工程上要把两个问题分开：页大小影响分裂频率和单页 I/O 粒度；键的插入位置分布影响长期填充率。要讨论吞吐、延迟或真实文件大小，还需要同一数据库版本、同一行格式和可复现的磁盘/缓存实验。

## 五、能做的工程选择：三个杠杆

1. **先验证键的插入位置分布**：自增或时间有序键可能更接近 append 路径，但不能把某个 UUID 版本直接承诺成“95%+ 填充”。真实结果还受批量大小、并发、二级索引、行大小和数据库实现影响，应在目标数据库上测叶页利用率与写入延迟。
2. **把页大小当作 I/O 粒度参数**：增大页通常能降低每行对应的分裂次数，但可能增加单页读写、缓存浪费和锁竞争代价；减小页也不会自动修复随机中间分裂。不要只看叶填充率做决定。
3. **接受随机键时考虑有边界的批量导入**：如果业务允许，先按主键排序再做 bulk load，可能改善初始填充；后续随机写入仍会改变页布局，必须把“导入阶段”和“稳态写入阶段”分开测量。

### 5.1 这个模型没有模拟什么

为了让表格可复现，模型主动省略了很多决定真实写放大的因素：

- InnoDB 的记录头、页目录、可变长行、压缩、聚簇索引和二级索引；
- buffer pool 命中与淘汰、redo/undo、checkpoint、doublewrite、fsync 和文件系统缓存；
- 并发插入、锁竞争、删除后的空洞复用、更新导致的迁移，以及重复键；
- 真正的磁盘吞吐、写缓存和故障恢复。

所以本文的“+43.5%”是**这个固定输入下的总页数差异**，不是生产数据库的写放大、吞吐或延迟承诺。

## 六、结论：随机主键把写放大藏进填充率

B+Tree 的可验证判断是：在固定行大小、页大小和插入数量下，顺序追加与随机中间分裂会产生不同的叶页填充率；本模型在 16KB 页、128B 行、20 万行、seed `20260817` 下得到 99.968% 对 69.661%，总页数相差 43.5%。这能解释空间和缓存压力的方向，但不能替代目标数据库上的 page split、buffer pool、redo、fsync 和恢复实验。想讨论自增键、时间有序键或随机 UUID，应先把这些指标在自己的行格式和并发模型下测出来，再决定是否改键。

下一步（本机，5 秒内）:

```bash
$ python3 experiments/btree-page-split/sim.py --rows 200000 --row-bytes 128
```

原始输出与环境记录在 `evidence/btree-page-split-write-amplification/2026-08-17-local/`。运行这个脚本只能复现教学模型；要把结论推进到生产方案，还需要在目标数据库上固定版本、行格式、索引、并发和存储设备，记录原始输出并加入删除、更新、恢复与故障场景。
