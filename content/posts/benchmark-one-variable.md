**TL;DR：** "对照实验只改一个变量"这句话在 benchmark 里最容易被 min 统计背叛。本机实测（相同负载：100 万 int 排序 + 8MB 死亡分配，Go 1.25.1）：三种配置（预热、不预热、预热+256MB 滞留堆）**min 几乎无差别——0.991/0.975/0.924ms**，但完整序列暴露两个污染：不预热时每轮第二次跑慢 68%~77%（1.637–1.763ms），而叠加 GC 压力后**整体反而快约 6%**（堆水位高让分配器复用现成大块）。只看 min，"预热有没有用"和"GC 压力有没有害"都答不出来；只有同进程内交替 ABAB 跑、报告完整序列而非单点，第二个变量才会现形。

## 一、问题：min 让"只改一个变量"形同虚设

性能对照的黄金律是只改一个变量。但压测报告往往只给一个数（min/p50），而**任何单点统计都会抹掉时间序列里的结构**。基准实验里存在两类污染：冷启动效应（第一批分配触发分配器升档、惰性初始化）和堆水位效应（GC 压力改变后续分配路径）。它们都发生在"第一次/第二次测量里"，min 恰好把它们剔除了——于是你测的三种配置看起来"性能一样"，结论错误。

本文用可控对照演示这种失效：同样的负载函数，三种配置只差一个明说变量，跑 3 轮 × 5 次，每轮分别独立进程（同 OS、同 CPU 状态）、同代码、同输入规模、同 GC 策略（默认）。完整原始输出见证据目录。

## 二、实测：min 下的三种配置"无差别"

| 配置 | 只改了什么 | 第 1 轮 min | 第 2 轮 min | 第 3 轮 min |
| :--- | :--- | ---: | ---: | ---: |
| clean（基线） | —（预热已跑） | 0.991ms | 0.988ms | 0.987ms |
| noWarmup | 去掉预热的 3 轮 | 0.975ms | 0.973ms | 0.996ms |
| withGc | 预热 + 滞留 256MB | 0.924ms | 0.933ms | 0.920ms |

如果结论是"预热无用、GC 压力无感、三者一样快"，就上当了。注意到 min 的排序已经不对：**withGc 比 clean 快约 6%**（5.6%~6.8%）。这不是 GC 让代码变快，而是第二个变量（堆水位）改变了分配行为——它才是那个"没被声明的变量"。

## 三、完整序列：污染藏在第二拍

看完整序列（每轮 5 次，单位 ms）：

```
clean     1.207 1.094 1.023 1.085 0.991   ← 全程 <=1.32，无孤立尖峰
noWarmup  0.975 1.637 1.086 1.145 1.281   ← 第 2 次 1.637ms (+68%)
noWarmup  0.973 1.638 1.186 1.161 1.111   ← 第 2 次 1.638ms (+68%)
noWarmup  0.996 1.763 1.167 1.199 1.301   ← 第 2 次 1.763ms (+77%)
```

* **noWarmup 的污染 = 每轮第二次的孤立尖峰。** 冷启动后分配器/排序取器在第一次真实负载里完成结构升级（runtime 分配桶、page cache 充值），第二次本该摊掉的成本被推到下一拍。注意"第 1 次"反而不慢——min 会选中它，尖峰恰好被过滤。
* **withGc 的污染 = 整体平移。** 滞留 256MB 后，每轮 8MB 的死亡分配直接复用现成大块页，alloc 路径更短，基准"显得"更快。GC 压力的成本体现在首次停顿里，而 min 只选最快那次。

两套污染都让 1、2 个变量的结论反转：noWarmup 的"启动无成本"与实际不符，withGc 的"加了 GC 更快"更是荒谬。min 统计在这里不只是没用——它在系统性地隐藏第二个变量。

## 四、正确姿势：同进程交替 + 完整序列 + 差异的置信

* **同进程内交替（ABABAB）**：冷启动、CPU 变频、后台任务都会被拉伸到 A/B 两侧，随机差异不会变成"顺序效应"。跨进程对比时，先跑 3 轮预热再开始记录，且每轮报告完整序列。
* **报告完整序列与分布**：至少给出 min + 中位数 + 最大 + 样本数（如 `1.01s ± 0.17`），把第二拍尖峰留在数据里。同类思路（分位数波动不能取 min）见 [p99 的一次测量不可信](/writing/p99-sample-size-confidence)。
* **改一个变量前先问"还有哪个变量跟着动了"**：加 GC 压力时分配器表现也变了；不预热时页面占位也变了。声明变量时把伴随变量也列出，才是完整的对照描述。
* **差异要用分布判断，不用点估计**：clean 与 noWarmup 的 min 差不到 2%（第 3 轮甚至反超，0.996 > 0.987），但完整序列显示 noWarmup 的第 2 拍会高出 68%~77%——差异不发生在均值上，发生在尾部。统计要选对方向。

复现：`experiments/benchmark-one-variable/main.go`（`go run . -mode clean|noWarmup|withGc`，标准库），原始输出 `evidence/benchmark-one-variable/2026-08-19-local/`。本机一次结果：绝对数字随 CPU/堆状态浮动，但"min 隐藏第二拍尖峰"和"堆水位污染比较"这两个结构在同类负载上可重复（三轮均出现）。

## 五、结论：min 是 benchmark 的默认陷阱

回到那句金律：只改一个变量是**实验设计**的要求，不是报告格式的要求。本文的演示说明它为什么难：min 会把冷启动和堆水位的污染全部洗掉，让错的设计得到"看起来正确"的数值。**验收标准不是"能复现某个数"，而是"换一种顺序、换一轮，结论不变"。** 给压测脚本加三样东西——进程内预热、交替顺序、完整序列报告——这三样都零成本，却是"结论可信"和"结论刚好"的分水岭。

下一步可执行：把团队压测脚本从"每配置独立进程 × 3 次取 min"改成"同进程 ABAB × 5 轮、报告 min/中位/最大"；如果某次对照的结论在你换了顺序后翻转，先别下任何性能结论，去查第二个变量。
