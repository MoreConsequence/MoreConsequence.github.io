**TL;DR：** 接手别人留下的事故时，最大的障碍不是技术，而是**传闻形态的证据**：数字在转述中各自漂移、命令指向已不存在的版本、结论找不到原始输出。本文用一个真实案例开场——同一篇事故稿里五组互相冲突的数字、一个连启动都会 `SyntaxError` 的"历史快照"——然后给出可执行的重建流程，并把"证据最小合同"做成体检工具跑在本仓库上：91 个证据目录只有 **24 个（26.4%）** 合同完整。结论：先保住分母和原始输出，再谈因果；实在找不回，就把"真实事故"降级为"构造演练"，这不可耻，编造才可耻。

## 一、同一事故，五组互相矛盾的数字

本仓库曾有一篇写成"47 分钟真实事故"的文章，审计时发现它至少有五组数字不能同时成立（登记于 `review.md` 第六节）：

| 说法 | 文中数字 | 可直接重算的结果 | 冲突 |
| --- | --- | --- | --- |
| 冷启动到 30 秒 RSS | 97.8MB → 241.2MB | 增量 143.4MB | 这组成立——唯一的锚 |
| 时间线 | "30 秒 +180MB" | 实测只增 143.4MB | +180MB 找不到基线 |
| TL;DR 分母 | 143MB / 1.5 万订单 | 约 9.56KB/订单 | 与同句"约 3 万订单"矛盾 |
| 若按 3 万订单 | — | 约 4.78KB/订单 | 不是文中的 9.5KB |
| 吞吐表 | 5834 vs 6274 req/s | 相对差约 7.54% | 正文却写"差 3%" |

还有更基本的裂缝："修复前"版本的代码根本无法启动——保留的历史文件导入了一个已被重构掉的导出名，Node 直接抛 `SyntaxError: does not provide an export named 'InMemoryOrderStore'`；正文让读者运行的压测脚本路径 `/tmp/postmany.lua` 从来没有生成步骤。

这就是传闻的形状：**每个局部听起来都合理，合在一起不可能同时为真**。此时任何"把 1.5 万改成 3 万"的修补都是猜测——可能成功创建了 1.5 万唯一订单而总请求 3 万，也可能 wrk 请求数、2xx 数、唯一 key 数被当成同一分母混用，甚至 bug 组和控制组的数字被交叉粘贴。没有原始输出之前，每一种复原方案都同样可信，也就同样不可信。

## 二、证据链的最小合同：三件套

一条能自保的证据链至少要有三件套，每一件回答一个别人稍后会问的问题：

```mermaid
flowchart LR
    A[结论/主张<br>claim] -->|由谁推导| B[派生公式与图表<br>derive]
    B -->|数据从哪来| C[原始输出<br>raw output]
    C -->|怎么跑出来的| D[命令与环境<br>cmd + env]
```

1. **环境记录**（Node/go 版本、OS、机器）：回答"换个环境还会是这个数吗"。性能数字离开环境就是谣言。
2. **完整命令**（可直接复制运行）：回答"我怎么验证你说的是真的"。命令里不许有 `/tmp/xxx` 这种凭空出现的依赖。
3. **原始输出文件**（未加工的 log/out）：回答"这个数是你算的还是你编的"。派生表格可以事后重算，原始输出不能重生成。

三件缺一的下场各不相同，但方向一致：缺环境，数字不可迁移；缺命令，结论不可复现；缺原始输出，争议时只能比谁的记性好。上面那篇事故稿三件全缺，于是它的每一个精确数字（9.5KB/订单、"差 3%"）都成了负债。

## 三、把合同变成可执行的体检

合同写在 README 里没人检查就等于没有。我把检查项做成了工具（`experiments/evidence-audit/audit.mjs`），对仓库全部证据目录逐项核对：有无 README、README 里有无运行时版本、有无可直接运行的命令块、有无原始输出文件、目录名能否回溯到对应的实验或文章。

对本体仓库的真实运行结果（`evidence/evidence-audit/2026-08-23-local/v4-final-table.md`）：

```text
- 目录总数: 91
- 完整合同(PASS): 24 (26.4%)
- 缺环境记录: 54
- 缺命令块: 42
- 无原始输出文件: 1
- slug 无法回溯到 experiments/posts: 5
```

**91 个证据目录，四分之三合同不完整。** 抽查证实这不是误报：比如某个 2026-08-19 的实验目录里躺着 `run.log` 和 `run.out`——原始输出都在，但没有任何 README 记录当时的环境和命令。再过半年，这些目录就是一批"只剩传闻"的事故现场，和第一节那篇文章的区别只是还没被人引用而已。

## 四、审计工具自己也要被审计

这次体检最有价值的产出不是那张表，而是工具自己的三次翻车现场，全部保留在证据目录里：

1. **v1**：env 判定正则区分大小写，把写作 `Node v24.19.0` 的记录判为缺失，PASS 只有 21——审计者的第一反应应该是怀疑审计器；
2. **v3 自举检查失败**：工具给自己的证据目录打了个 GAP——我给目录起了 `evidence-audit-first-run` 这种带修饰后缀的名字，破坏了"目录名 = 工件名"的回溯规则，而且 `.md` 数据表没被计为原始输出。同一个坑一天摔两次；
3. **v4 终版**：修正后 PASS 24（26.4%），工具自身的行转为 PASS，自举闭环。

这暴露了体检的一个结构性事实：**检查器和它检查的东西一样会腐烂**。所以体检结果必须连同工具版本一起报关（本目录 README 同时记录了四个版本的差异），否则半年后有人复跑出不同数字，又是一桩悬案。

## 五、重建的顺序与它的边界

接手事故现场的实操顺序，按投入产出排序：

1. **先固定还能固定的**：把现存进程的版本、启动参数、内核参数抓下来——它们随时间衰减最快；
2. **考古 git 历史**：找出事故对应版本的 commit，验证它能否启动、能否编译——本案例证明"历史快照"经常连语法都过不了；
3. **重算所有能重算的**：文中每个比例、增量、百分比手工重算一遍（第一节的表就是这么来的，五组冲突全是除法除出来的）；
4. **补跑构造实验**：历史现场找不回，就在当前代码上构造等价反例，并明确标注"这是演练不是历史"；
5. **降级不可证实的部分**：删掉所有找不到锚点的精确数字。

第 4 步正是那篇事故稿的最终归宿：它被改写为构造事故演练，"47 分钟真实事故"的叙事和无法证实的 RSS 数字一并删除，只保留可重跑的 500/100 构造数字。[诚实降级](/writing/service-incident-drama)不是失败——把猜测包装成测量才是。

同时说清体检的边界：它只检查合同字段的**在场性**，不判断内容对错。一个目录可以环境、命令、原始输出俱全，但结论照样错；在场性是必要条件，不是充分条件。判定用的正则是启发式的，设计取向是宁漏报勿误报。另外两点：表中数字是 2026-08-23 运行时点的快照，仓库继续新增证据目录后复跑会得到不同总数；本工具与仓库更早的 `scripts/evidence-audit.mjs` 是两份独立实现（后者先存在，本次为配合审计口径另建），合并是待办而不是既成事实。

## 六、结论：先保住分母，再谈因果

事故复盘最贵的错误不是找错根因，而是在分母都没对齐的情况下就开始归因。本文的可执行清单：

1. 给你的证据仓库定一份三件套合同：环境、命令、原始输出，一件都不能少；
2. 把合同变成脚本体检，每次写完实验顺手跑一遍——人靠不住，闸门要自动化；
3. 证据目录名必须等于工件名，禁止任何修饰后缀（我自己一天摔了两次的地方）；
4. 接手传闻事故时先重算再相信，找不回原始输出的精确数字一律删除或降级。

这份清单现在就能用：对你仓库的实验与事故记录跑一次同款盘点，把 GAP 清单原样贴进下一个迭代的待办——那 74% 的缺口不需要决心，只需要排期。
