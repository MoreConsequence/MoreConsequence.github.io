**TL;DR：** `append` 的扩容税比直觉大得多：切片从 0 增长到 100 万元素，要经历 **41 次搬家**，累计拷贝量 = 2+4+8+…+最终容量 ≈ **最终容量的 4.9 倍**；这是累计搬运量，不是常驻内存。统一 benchmark（`experiments/go-runtime-boundary`，Go 1.25.1/arm64）对 65536 个 int 的三次 run 得到：自然增长 **0.30–0.58ms / 26 allocs / 2.51MB**，预分配 **0.067–0.088ms / 1 alloc / 0.52MB**。时间区间受 CPU 频率和 GC 影响，但分配次数与字节数稳定说明了扩容税。扩容策略（Go 1.18+）仍以 256 元素为分界：以下翻倍，以上平滑接近 1.25 倍。

## 一、扩容策略：256 元素的分界线

Go 1.18 之后 `growslice` 的容量算法（runtime/slice.go:296）：

```go
const threshold = 256
if oldCap < threshold {
	return doublecap        // <256：直接翻倍
}
for {
	// ≥256：1.25 倍起步，平滑过渡
	newcap += (newcap + 3*threshold) >> 2
	...
}
```

翻倍 vs 1.25 倍的取舍：翻倍省搬家次数（摊薄拷贝），但内存峰值浪费大（可能浪费一半容量）；1.25 倍省内存但搬家更频繁。256 是实测折中点：小切片翻倍（搬 1 次的成本远小于分配成本），大切片 1.25 倍（1 亿元素的切片一次搬家是 8 亿字节 memmove，不值得为省一次搬家付出 25% 常驻内存）。从 0 增长的完整序列：

```
1, 2, 4, 8, ..., 128, 256, 512, 832, 1232, 1732, ...
      ← 翻倍段 →         ← 1.25x 平滑段 →
```

注意 512 之后不是 1024——是 832。**翻倍在 256 处戛然而止**，之后每次增长约 25~30%。

## 二、4.9 倍税：几何级数的摊薄成本

总拷贝量 = 每次扩容搬走旧数据之和 = 2+4+8+…+最终容量 ≈ 2×最终容量（翻倍段）加上大容量段的 1.25x 序列，模拟完整增长（到 100 万元素）：

| 起始容量 | 扩容次数 | 累计拷贝（×终点容量） |
|---|---|---|
| 0 | 41 | 4.90 |
| 8 | 37 | 4.90 |
| 256 | 32 | 4.90 |
| 4096 | 25 | 4.87 |

**起始容量不改变总拷贝比例——永远约 4.9 倍**。41 次扩容里每次搬得越来越多，最后几次占了大头：从 512K 到 1M 那一次就搬了 51 万元素，比前 40 次加起来还多。这就是"自然增长"的隐性账单：**你不是多花了 4.9 倍的内存，是搬了 4.9 倍的数据**——CPU 时间、cache 污染、GC 压力全在这一条里。

## 三、实测：分配字节稳定，墙钟时间要看原始区间

本机实测（Go 1.25.1，arm64 8 核，append 65536 个 int）：

| 方式 | 耗时 | allocs | 分配内存 |
|---|---|---|---|
| 自然增长 `var s []int; append×65536` | **0.30–0.58ms** | 26 | **2.51MB** |
| 预分配 `make([]int, 0, 65536)` | **0.067–0.088ms** | 1 | **0.52MB** |

内存差 2.51/0.52 = **4.8 倍**；它接近但不等于累计拷贝量的 4.9 倍，因为 B/op 还受容量取整和分配器 size class 影响。三次 run 的时间区间约为 **3.4–8.4 倍**，不能压成一个稳定常数；可重复的判断是：26 次扩容带来更多分配和 memmove，`make` 的容量参数把终点提前告诉运行时。

## 四、生产判断：容量参数怎么给

| 场景 | 判断 | 依据 |
|---|---|---|
| 能估算上界（读文件、读响应） | `make([]T, 0, 估算)` | 当前基线少 25 次分配，分配字节约降到 1/4.8 |
| 完全不知道（流式追加） | 自然增长 | 4.9 倍税在总耗时里通常可接受 |
| 多次 append 同一个切片 | 循环外先 make | 每轮 append 都会扩容，税重复缴纳 |
| 大元素（≥KB 的 struct） | 存指针或预分配 | 搬家成本随元素大小线性放大 |
| 切片作为参数传递 | 注意容量别误导 | 见下文：cap 是契约不是建议 |

一个常被误解的细节：`make([]int, 0, 65536)` 与 `make([]int, 65536)` 不同——前者零值初始化 0 个元素、后续 append 不扩容；后者直接给 65536 个零值（更贵的内存清零）。**只 append 不读初始值，用前者**（呼应《[mallocgc 解剖](/writing/go-mallocgc-allocator)》的分配成本：清零是 256B 以上分配的主要成本）。

## 五、结论：可估算上界时预分配，别让 append 替你搬家


append 的扩容税是"约 4.9 倍累计拷贝 + 26 次分配"，统一 benchmark 复现了 2.51MB 对 0.52MB 的分配差异；墙钟时间则应以当前机器的原始区间为准。Go 1.18+ 的策略在 256 元素处分界：以下翻倍、以上平滑接近 1.25 倍。生产规则一句话：**能估算上界就 make 预分配，估算不了才让 append 自然生长**。

下一步可做的事：扫一遍你代码里循环内的 `append`（尤其读文件/响应的），凡循环前能算出行数的，加 `make` 预分配并对照 benchmark。
