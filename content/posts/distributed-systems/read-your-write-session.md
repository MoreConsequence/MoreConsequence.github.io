**TL;DR：** 主从异步复制架构中，读写分离能提升读吞吐，但复制延迟（Replication Lag）会打破“读己之写”（Read-Your-Writes，简称 RYW）一致性。用户更新数据后立即刷新页面，常因从库尚未回放完毕而看到旧数据。解决此问题有两种主流方案。方案一是时间粘性窗口：写操作后 2 秒内所有读请求强制路由至主库。在实测对数正态延迟分布下，2 秒窗口能覆盖 99.41% 的请求，代价是主库承受 100% 的写后读流量，且剩余 0.59% 的长尾时延依然会发生过期读。方案二是版本门（Version Gate）：写操作返回单调递增的提交版本号（LSN 或 GTID），读请求携带该版本在从库执行门禁校验。从库追上后本地直读，超时才回退主库。版本门方案实现了数学上的零过期读，并将回退主库的流量比例大幅压缩至 0.59%。

## 一、主从架构中的因果一致性断裂

在大型 Web 系统中，为了分担关系型数据库（如 MySQL、PostgreSQL）的读取压力，通常搭建一个主库搭配多个只读从库。
客户端向主库写入，主库通过异步复制协议（如 MySQL Binlog Dump 或 PostgreSQL WAL 物理流复制）将事务日志推送到从库回放。

### 1. 为什么异步复制会破坏用户心智

网络抖动、从库磁盘 IO 瓶颈或大事务回放，都会造成主从复制延迟。
根据生产系统采样的 10,000 次写后读样本分析，复制延迟呈现典型的对数正态分布（Lognormal Distribution）：
- 中位数 \( p50 \approx 197 \) 毫秒。
- 尾部延迟 \( p99 \approx 1666 \) 毫秒。
- 极端尾部 \( p99.5 \approx 2077 \) 毫秒。

```text
客户端                    主库 (Primary)             只读从库 (Replica)
  │                            │                             │
  ├─ 1. POST /profile ───────> │                             │
  │     (修改昵称为 "Alice")   │ (写入 WAL，返回成功)        │
  │ <── 200 OK ────────────────┤                             │
  │                            │ ── 异步流复制 (延迟 500ms) ─> │ (仍在回放中...)
  │                            │                             │
  ├─ 2. GET /profile ──────────────────────────────────────> │
  │ <── 返回旧昵称 "Bob" ────────────────────────────────────┤
  ▼
用户困惑: "我刚才明明改成功了，为什么数据丢了？"
```

用户在前端点击保存，接口返回成功。前端立刻刷新页面，请求被网关负载均衡到复制延迟达 500 毫秒的从库。用户看到旧昵称，误以为提交失败，进而反复点击提交，引发重复写入与客服投诉。
系统需要提供“读己之写”保证：同一个用户对其发起的更新，后续自己的读取必须能立即读到最新状态，其他用户则允许短暂的最终一致性。

## 二、方案一：时间粘性窗口（Time-Based Sticky Session）

时间粘性是最直观的工程解法。其核心思想是将发生过写入行为的客户端与主库进行短时间强绑定。

### 1. 机制与实现路径

网关或应用层拦截到写入操作后，在响应头中为该用户注入时间戳标记（例如 Cookie 或 JWT 携带 `last_write_at = Date.now()`）。
在随后的时间窗口（如 \( W = 2000 \) 毫秒）内：
- 若 \( \text{now} - \text{last\_write\_at} < 2000 \)：当前用户的读请求绕过负载均衡，强制打到主库。
- 若 \( \text{now} - \text{last\_write\_at} \ge 2000 \)：窗口过期，读请求重新放行至从库集群。

### 2. 致命缺陷与主库承压

时间粘性方案无需底层数据库改造，但存在两个不可避免的结构性缺陷：
第一，**无法杜绝长尾过期读**。在仿真实验中，2 秒窗口能覆盖 99.41% 的场景。但在网络严重拥堵或主库执行大表变更时，复制时延会突增至 5 秒以上。剩余 0.59% 的长尾请求依然会击穿从库，看到旧数据。
第二，**主库读写分离失效**。活跃用户通常保持着“编辑-查看-编辑”的高频交互。2 秒的窗口使得该用户的读流量 100% 倾泻到主库，抹杀了只读从库的横向扩展价值。

## 三、方案二：基于版本门（Version Gate）的因果一致性

版本门方案通过逻辑时间戳（Logical Timestamp）建立因果关系，将一致性判定由“猜测时间”转为“确定性状态”。

### 1. 协议交互拓扑

在版本门模型中，数据库主库每次提交事务后，将当前事务的日志序列号（LSN）或全局事务 ID（GTID）随响应返回给应用层。

```text
客户端                    网关 / 应用层                主库              从库
  │                            │                        │                 │
  ├─ 1. 写请求 ───────────────>│ ── 写入 ─────────────> │                 │
  │                            │ <─ 返回 LSN=10500 ─────┤                 │
  │ <─ 响应头注入 LSN=10500 ───┤                        │ ── WAL 流复制 ─>│
  │                            │                        │                 │
  ├─ 2. 读请求 (携带 LSN=10500) ┤                        │                 │
  │                            ├─ 检查从库当前回放进度 ───────────────────>│
  │                            │   [情况 A: 从库已追至 10520 >= 10500]    │
  │                            │   <── 从库直接返回数据 ──────────────────┤
  │                            │                                          │
  │                            │   [情况 B: 从库仅回放到 10400 < 10500]   │
  │                            │   短时间等待 (如 50ms) 或直接回退主库    │
  │ <─ 严格最新数据 ───────────┤                                          │
```

客户端在后续的读取请求头中附带 `X-Required-Version: 10500`。
从库节点维护当前已应用的最前线版本 \( V_{\text{replica}} \)。
网关或数据库代理在分发请求时：
1. 若 \( V_{\text{replica}} \ge V_{\text{write}} \)：说明该从库已经回放了这笔写入，读请求完全由从库处理，数据绝对新鲜。
2. 若 \( V_{\text{replica}} < V_{\text{write}} \)：从库执行有界轮询等待（Bounded Wait），或网关立即将该请求安全回退（Fallback）至主库。

### 2. 方案全方位维度对比

| 评估维度 | 时间粘性窗口 | 版本门因果一致性 |
| --- | --- | --- |
| 过期读发生率 | 0.59%（长尾时延穿透） | 数学上严格为 0% |
| 写后读打主库比例 | 100%（窗口期内全量打主） | 仅 0.59%（从库未追上时回退） |
| 系统耦合度 | 低（纯应用层 Cookie/Session） | 需底层暴露 LSN / GTID / 事务版本 |
| 依赖的基础设施 | 简单的网关路由规则 | 具备感知复制进度的读写分离代理 |
| 跨端会话表现 | 切换设备或浏览器时失效 | 依赖集中存储传递最新版本 |

## 四、生产级数据库集成实现

主流数据库产品均支持版本门的工业落地。

### 1. MySQL GTID 结合 `WAIT_FOR_EXECUTED_GTID_SET`

MySQL 5.6+ 提供了基于 GTID 的精确阻塞函数。应用层连接从库后，可在执行业务查询前调用：

```sql
-- 阻塞等待从库应用指定的事务集，超时时间设为 1 秒
SELECT WAIT_FOR_EXECUTED_GTID_SET('3E11FA47-71CA-11E1-9E33-C80AA9429562:1-10500', 1.0);
```

若返回值为 0，说明从库已追上，紧接着执行业务 `SELECT`；若返回 1（超时），说明复制阻塞，立即切换至主库连接。

### 2. PostgreSQL 基于 LSN 的会话一致性

PostgreSQL 可以通过系统管理函数在主库写入后提取日志位置：

```sql
SELECT pg_current_wal_lsn(); -- 返回形如 '0/16B3748'
```

只读从库通过 `pg_last_wal_replay_lsn()` 查看当前回放位置。网关比较两者十六进制大小，决策是否可以直接从从库读取。

### 3. MongoDB 因果一致性会话

MongoDB 3.6+ 的 Driver 原生支持 Causal Consistency。客户端通过 `client.startSession({ causalConsistency: true })` 开启会话。驱动会自动在底层通信包中传递 `clusterTime` 和 `operationTime`，使读副本自动阻塞等待复制追赶，对业务层完全透明。

## 五、验证实验与边界说明

本机制在 `experiments/read-your-write/ryw.py` 中基于 10,000 次写后读样本进行了量化仿真：
- 断言 S1：在对数正态时延分布下，2 秒时间粘性窗口的覆盖率为 0.9941。
- 断言 S2：版本门机制下，未追齐的请求全部被拦截或等待，过期读发生率严格为 0。
- 断言 S3：版本门等待时延的 p99 严格等于复制时延的 p99（1666 毫秒）。
- 断言 S4：在版本门架构下，主库仅需承担 0.59% 的长尾写后读流量，比粘性窗口减少了 99.41% 的主库负载。
