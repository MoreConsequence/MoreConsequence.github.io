**TL;DR：** token 是 LLM 计费和上下文窗口的基本单位，不是字符也不是词。o200k 分词器下实测：中文约 1 字 = 1 token，英文约 4.7 字符 = 1 token，代码约 3.8 字符 = 1 token；编码是确定性的（同一文本每次切分结果相同）。GPT-4.1 的输入/缓存命中/输出价格快照是 **$2.00/$0.50/$8.00 每百万 token**。在每天 1 万次、每次输出 300 token 的客服模型中，裸 prompt 40 token 月成本为 **$744**；系统提示 + 2K 文档且 90% 稳定前缀命中时为 **$1,427**；文档增至 20K 后为 **$4,936**。**prompt 结构决定的输入 token 体量，比模型单价更决定账单**，但缓存命中 token 不是免费 token，必须按缓存价单独计费。

## 一、 token 不是字符：先实测，再谈钱

所有关于 LLM 账单的讨论都从一个反直觉的事实开始：**计费单位既不是字符也不是单词**。OpenAI 用 Byte-Pair Encoding（BPE）子词分词器（o200k），把文本切成模型词汇表里的 token id，按 token 数计费。

我用 OpenAI 官方开源的 tiktoken 分词器（o200k_base，GPT-4o/GPT-4.1 统一使用）在本机实测五类文本，`experiments/llm-token-economics/measure.mjs` 可复现：

| 文本类型 | 字符数 | token 数 | 字符/token |
| --- | --- | --- | --- |
| 中文一句话（47 字） | 47 | 32 | 1.5 |
| 英文一句话（137 字符） | 137 | 29 | 4.7 |
| TypeScript 代码（19 行） | 197 | 52 | 3.8 |
| JSON 对象（99 字符） | 99 | 38 | 2.6 |
| 中英混排（64 字符） | 64 | 37 | 1.7 |

再做一次精确测量：一段 141 字的中文段落切成 100 个 token，**1 字 ≈ 1 token**。换算成直观数字：100 万 token 的上下文窗口，大约装得下 100 万汉字的小说；而同样的窗口英文能装约 470 万字符。

编码确定性也被实测确认：同一文本调用 3 次，token 数都是 32、id 序列完全一致。这保证了**成本计算可以离线、精确、复现**——不需要真模型，tokenizer 就能告诉你答案。

## 二、 三档定价：输入、输出与缓存，为什么输出贵 4 倍

2026-08-16 核对的官方价格快照，单位：美元/百万 token；价格会变，本文成本模型只使用 GPT-4.1 这一行，其他行用于说明不同供应商的缓存价差：

| 模型 | 输入 | cached 输入 | 输出 | 上下文/备注 |
| --- | --- | --- | --- | --- |
| GPT-4.1（OpenAI） | $2.00 | $0.50（75% off） | $8.00 | 1,047,576 context window |
| Claude Sonnet 4.6（Anthropic） | $3.00 | $0.30（10%） | $15.00 | 另有 5m/1h cache write 价格 |
| Claude Opus 4.6（Anthropic） | $5.00 | $0.50（10%） | $25.00 | 另有 5m/1h cache write 价格 |
| Claude Haiku 4.5（Anthropic） | $1.00 | $0.10（10%） | $5.00 | 模型/平台需单独核对 |

两个结构性问题，比具体数字更重要：

**输出贵不是定价策略，是计算成本决定的。** 输入处理是并行的：整段 prompt 一次前向传播完成预填充（prefill），TTFT 只取决于首批 token。输出是串行的：每生成一个 token 都要做一次前向传播，且全程要保留 KV cache（键值缓存）供注意力读取。生成 1000 个 token ≈ 1000 次串行前向传播，这就是输出单价是输入 4 倍、且延迟以"秒"计的物理原因。

**缓存的语义是"读折扣"，不是"免费"。** Anthropic 的缓存写（cache write）比普通输入贵 25%（1.25×），OpenAI 的缓存写按普通输入计；而缓存命中（cache hit/read）在 Anthropic 打 1 折（$2→$0.20），在 OpenAI 打 2.5 折（$2→$0.50）。设计含义：**稳定前缀（系统提示、工具定义、文档上下文）排在 prompt 前面并标记可缓存，命中率会决定你真实成本的 1-2 位数。**

## 三、 成本账本：同一条业务请求，prompt 结构决定账单数量级

数字不骗人。我用 2026-08 的 GPT-4.1 官价（输入 $2/M、输出 $8/M、缓存命中 $0.5/M）建了一个客服 Agent 的成本模型（`experiments/llm-token-economics/cost-model.mjs`，可复现）：

> 场景：客服 Agent，30 天 × 每天 1 万次请求，每次输出固定 300 token，输入分五种结构。

| prompt 结构 | 输入总量/次 | 未缓存/次 | 缓存/次 | 缓存命中 | 月成本 |
| --- | --- | --- | --- |
| 裸调用（40 token） | 40 | 40 | 0 | 0% | $744 |
| 加 1500 token 系统提示，不缓存 | 1,540 | 1,540 | 0 | 0% | $1,644 |
| 系统提示 + 2K RAG 文档，不缓存 | 3,540 | 3,540 | 0 | 0% | $2,844 |
| 同上，启用缓存（90% 命中） | 3,540 | 390 | 3,150 | 90% | $1,427 |
| 系统提示 + 20K 文档，启用缓存 | 21,540 | 2,190 | 19,350 | 90% | $4,936 |

三个直接结论：

1. **输入 token 体量是最大变量**：在脚本的“全部按普通输入计费”对照中，输入从 40 增到 20,000 token/次，月账单从 $744 到 $12,720，约 17.1 倍；这不是 20K 文档缓存场景的数字，不能混用。
2. **缓存让同样结构省约 50%**：系统提示 + 2K 文档从 $2,844 降到 $1,427；计算把 390 个未缓存 token 按 $2/M、3,150 个缓存命中 token 按 $0.5/M 计费。
3. **RAG 文档体积仍是隐藏炸弹**：在 90% 稳定前缀命中下，2K 文档到 20K 文档使月账单从 $1,427 增至 $4,936，约 3.5 倍；每增加 1K 稳定且 90% 命中的 token，按当前请求量约增加 $195/月，若完全不缓存则约增加 $600/月。

输出侧同样放大：输入恒 2K 时，输出 100 → 1000 token/次，$1,440 → $3,600（2.5 倍）。生成型任务（写文章、总结）的账单几乎由输出长度决定。

## 四、 窗口不是内存：满了之后发生什么

上下文窗口 1M token 听上去很大——那是对英文而言够装《三体》三部曲的量级；但你的 Agent 每轮对话都在重新消费它：

- **每轮都付全价**：API 无会话态，每轮请求都要把历史上下文重新发一遍（除非命中缓存）。一轮 10 次工具调用的 Agent 走完，输入 token 是单次调用的 10 倍起。
- **满了没有"溢出"，只有取舍**：超窗请求直接被拒绝（422 context_length_exceeded）。工程上的三种应对——**截断**（丢最早历史，模型忘了前文）、**压缩**（摘要替代原文，信息丢失）、**外挂检索**（只带相关片段进窗口，成本最低但依赖检索质量）——本质都是在"遗忘程度"和"成本"之间选点。
- **缓存 TTL 让结构失效**：Anthropic 缓存 5 分钟/1 小时 TTL，OpenAI 缓存有自动失效策略且对长 prompt 分段。如果 Agent 每轮间隔超过 TTL，缓存形同虚设，账单回到全价——**缓存的敌人不是冷启动，是慢会话**。

## 五、 结论：先算 token 账，再谈架构

- 账单的第一变量是**输入 token 体量**，不是模型单价：在本文 90% 命中模型中，20K 文档场景是 $4,936/月；完全不缓存时则是 $13,644/月，缓存语义会改变结论的分母。
- 缓存的正确姿势是**把稳定前缀放前面并标记可缓存**，同时监控缓存命中率——它是 prompt 结构健康度的仪表盘。
- 中文用户要警惕：1 字 ≈ 1 token 的高密度意味着同样的功能需求，中文 prompt 消耗的 token 比英文多约 30%（按字符/token 换算），预算规划要按 token 算，不能按字数算。

下一步可执行的事：用 `tiktoken`（`npm i tiktoken`）给现有 prompt 做一次离线 token 审计，算出"系统提示 + 文档上下文"占输入的百分比；超过 50% 且有稳定前缀，就标记缓存并盯命中率。算完账再看下一篇文章：相同预算下，embedding 检索的取舍如何进一步压缩输入。
