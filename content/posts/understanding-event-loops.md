我们常用“一条不断取任务的循环”解释事件循环。这个比喻适合入门，却容易掩盖真正重要的细节：浏览器同时协调任务队列、微任务检查点、渲染机会和多个执行环境。

## 先区分任务和微任务

脚本、定时器回调与用户交互通常进入任务队列。Promise reaction 和 `queueMicrotask` 进入微任务队列。

```js
console.log("A");

setTimeout(() => console.log("B"));
queueMicrotask(() => console.log("C"));

console.log("D");
// A, D, C, B
```

当前任务结束后，运行时会清空微任务队列，然后才可能进入渲染或下一个任务。

## 渲染不是每轮必做

浏览器会结合刷新率、页面可见性和主线程占用决定何时渲染。把 `setTimeout(fn, 0)` 理解成“下一帧”并不准确；需要与绘制同步时，`requestAnimationFrame` 才表达了正确意图。

## 微任务也会阻塞

微任务可以继续创建微任务。如果这条链一直增长，浏览器就没有机会处理输入或绘制页面。

> 异步 API 不等于并行，也不天然等于流畅。决定体验的是每段工作占用主线程的时长，以及它把控制权交还给浏览器的时机。

## 用时间线而不是口诀

排查顺序问题时，画出当前调用栈、任务、微任务和渲染机会，通常比背诵输出顺序更可靠。模型越接近真实调度，越能解释性能问题。
