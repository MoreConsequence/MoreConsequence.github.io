## 1. 面试考点还原：从单点库存到多维区间库存

在顶级互联网公司的资深系统设计面试中，考官往往会通过与普通电商秒杀的对比切入：

> **面试官提问：**  
> “我们现在要为一家全球连锁酒店集团设计核心预订引擎，支撑日均 500 万订单、峰值数万 QPS 的热门度假酒店秒杀。  
> 1. **多维库存的物理挑战**：普通电商下单是 `stock = stock - 1`，但酒店预订是跨日期的。用户 A 预订 10月1日到 10月4日（占 1、2、3 日），用户 B 预订 10月3日到 10月6日（占 3、4、5 日）。如何设计底层库存表结构，既能支持高频并发扣减，又能支持用户查询‘未来 30 天哪天有空房’？  
> 2. **死锁灾难**：如果采用数据库事务悲观锁，用户 A 并发锁定 [1日, 2日, 3日]，用户 B 并发锁定 [5日, 4日, 3日]。系统为什么极大概率触发数据库死锁（Deadlock Exception）？如何从算法层面彻底证明并根除死锁？  
> 3. **两阶段预留与超时释放**：用户下单后锁定房间 15 分钟，若 15 分钟内未完成付款，房间必须自动释放回库存池供其他用户抢购。如果每秒有 10,000 笔订单未支付，你难道要在数据库里每秒执行一次 `SELECT * FROM orders WHERE status = 'UNPAID' AND created_at < NOW() - 15m` 吗？这会导致什么灾难？如何优雅实现？  
> 4. **超订（Overbooking）与防超卖矛盾**：五星级酒店通常允许 10% 的合理超订（防止旅客临时取消导致客房空置）。但超订如果失控，会导致旅客到店无房，引发巨额法律索赔。系统如何在保证不发生意外超卖的前提下，优雅支持可配置的弹性超订？”

## 2. 核心数学难题：连续多维区间的死锁消除定理

在讨论并发控制前，必须先在理论层面解决多资源并发锁定的**死锁问题**。

### 2.1 交叉锁定引发的经典死锁复现

假设数据库中按天记录库存，主键为 `(room_type_id, date)`。
- **事务 A（用户 A 预订 10月1日 到 10月3日，需锁定 10-01 与 10-02 两天）**：
  ```sql
  -- 事务 A 执行
  SELECT * FROM room_inventory WHERE date = '2026-10-01' FOR UPDATE; -- 成功获取 10-01 锁
  SELECT * FROM room_inventory WHERE date = '2026-10-02' FOR UPDATE; -- 等待事务 B 释放！
  ```
- **事务 B（用户 B 预订 10月2日 到 10月4日，需锁定 10-02 与 10-03 两天）**：
  若由于前端传参或系统遍历顺序无序，事务 B 恰好先执行了：
  ```sql
  -- 事务 B 执行
  SELECT * FROM room_inventory WHERE date = '2026-10-02' FOR UPDATE; -- 成功获取 10-02 锁
  SELECT * FROM room_inventory WHERE date = '2026-10-01' FOR UPDATE; -- 等待事务 A 释放！
  ```

```
[多日期交叉锁死图 (Deadlock Cycle)]

  [ 事务 A ] -- 持有 10-01 锁 --> 等待 10-02 锁 --+
      ^                                          |
      |                                          v
      +-- 等待 10-01 锁 <-- 持有 10-02 锁 -- [ 事务 B ]

【结果】：两个事务互相持有对方需要的资源，形成循环等待（Circular Wait），
触发 InnoDB 死锁检测机制（Deadlock detected），其中一个事务被强行回滚！
```

### 2.2 1965 年 Dijkstra 的死锁破坏公理：全局资源全序锁定

1965 年，计算机先驱 Edsger W. Dijkstra 在提出哲学家就餐问题时确立了并发死锁的数学准则：
> **Edsger W. Dijkstra.** *"Cooperating sequential processes."* Technological University Eindhoven (1965).

死锁发生必须同时满足四个充分必要条件：互斥、占有且等待、不可抢占、**循环等待（Circular Wait）**。
消灭死锁最彻底、性能开销最小的办法，就是从数学上**破坏循环等待条件**：

$$\text{若对所有系统资源建立一个全局严格单调递增的全序关系 } \mathcal{R}_1 < \mathcal{R}_2 < \dots < \mathcal{R}_n$$
$$\text{所有并发事务必须严格按照该全序顺序申请资源锁，则系统中绝不可能产生环路！}$$

**工业级落地军规：**  
在预订系统应用层，无论前端用户传入的日期区间是什么、无论跨越多少个自然月，在进入库存锁定逻辑前，**必须对涉及的所有日期执行严格的自然升序排序（`dates.sort()`）**！
所有事务都必须统一按照 `10-01 -> 10-02 -> 10-03` 的确定性物理方向逐一申请加锁。只要排序规则绝对确定，拓扑图中的有向边永远单向流动，**从数学底层彻底消灭死锁**。

## 3. 底层数据模型与并发控制三剑客选型

如何设计支撑区间检索与扣减的数据库表？

### 3.1 关系型数据库模型设计

```sql
CREATE TABLE room_type_inventory (
    hotel_id BIGINT NOT NULL,
    room_type_id BIGINT NOT NULL,
    date DATE NOT NULL,
    total_inventory INT NOT NULL,     -- 物理总房间数 (如 100)
    reserved_count INT NOT NULL DEFAULT 0,  -- 处于预留占用状态的房间数
    overbooking_limit INT NOT NULL DEFAULT 0, -- 允许超订的额外额度 (如 10)
    version INT NOT NULL DEFAULT 0,   -- 乐观锁版本号
    PRIMARY KEY (hotel_id, room_type_id, date)
);
```
- **核心判定准则**：
  $$\text{可用库存（Available）} = \text{total\_inventory} + \text{overbooking\_limit} - \text{reserved\_count}$$
- 预订 $N$ 间房的前提是：连续区间内的**每一天**都必须满足 $\text{Available} \ge N$。

### 3.2 方案对比：悲观锁 vs 乐观锁 vs Redis Lua 原子操作

面对每秒数万次的并发秒杀预订，哪种方案能够胜任？

```
[三大并发库存控制方案的物理瓶颈演进]

方案 1: 数据库悲观锁 (SELECT ... FOR UPDATE)
+-------------------------------------------------------------+
| 优点: 逻辑最严密，绝对不超卖。                                |
| 缺点: 高并发下大量数据库线程挂起等待行锁，连接池 (HikariCP)   |
|       瞬间打满，慢查询雪崩，全站接口响应时间从 10ms 飙至 5s+!  |
+-------------------------------------------------------------+

方案 2: 数据库乐观锁 (CAS Version Check)
+-------------------------------------------------------------+
| 优点: 无数据库行锁，读性能极好。                              |

+-------------------------------------------------------------+

+-------------------------------------------------------------+
| 优点: 纯内存单线程执行，无锁并发，微秒级响应 (50,000+ QPS)。   |

+-------------------------------------------------------------+
```

## 4. Redis Lua 脚本实现连续日期原子预扣

在现代千万级预订架构中，**将高频库存预留操作彻底前置至 Redis 内存层**是公认的标准模式。

### 4.1 Redis 数据结构建模

在 Redis 中，我们为每一个“酒店+房型”按天建立一个 Hash 键：
`Key: inv:{hotel_id}:{room_type}:{yyyyMMdd}`
Fields:
- `total`: 物理总房间数（例如 100）
- `reserved`: 当前已预留房间数（例如 25）
- `overbooking`: 允许超订额度（例如 5）

### 4.2 连续日期全原子预扣 Lua 脚本（All-or-Nothing）

为了保证“连续 5 天要么全扣成功，要么一条都不扣”的原子性，必须在一段 Lua 脚本中执行**“两遍扫描（Two-Pass Scan）”**：

```lua
-- KEYS: 涉及的连续日期库存键列表 [inv:1:101:20261001, inv:1:101:20261002, ...]
-- ARGV[1]: 预订房间数 (num_rooms, 如 2)
-- 返回值: 1 表示成功预留; -1 表示库存不足 (触发原子放弃)

local num_rooms = tonumber(ARGV[1])

-- 第一遍扫描: 预检查所有日期的库存是否充足 (Dry-Run Check)
for i, key in ipairs(KEYS) do
    local total = tonumber(redis.call('HGET', key, 'total') or '0')
    local reserved = tonumber(redis.call('HGET', key, 'reserved') or '0')
    local overbooking = tonumber(redis.call('HGET', key, 'overbooking') or '0')
    
    local available = total + overbooking - reserved
    if available < num_rooms then
        -- 只要其中任意一天库存不足，整单原子放弃，绝不执行任何修改！
        return -1
    end
end

-- 第二遍扫描: 所有日期均满足条件，执行真正的原子扣减 (Atomic Execution)
for i, key in ipairs(KEYS) do
    redis.call('HINCRBY', key, 'reserved', num_rooms)
end

return 1
```

**物理优势：**  
由于 Redis 内部以单线程模型执行 Lua 脚本，整段脚本的执行具有**天然的互斥性与原子隔离性**。在并发请求下，不存在任何时间缝隙（Race Condition），单台 Redis 分片即可支撑每秒 50,000 次以上的多日期连续预扣，彻底消除了数据库的并发压力。

## 5. 两阶段预留（Hold-Confirm）与 15 分钟超时关单闭环

用户在点击“立即预订”后，系统不能直接把房间永久划走，必须经过**“下单预留（Hold） $\to$ 支付确认（Confirm）”**的生命周期。

```
[预订系统的完整两阶段生命周期]

[ 用户点击预订 (选定 10-01 至 10-06) ]
                  |
                  v 步骤 1: Redis Lua 执行两遍扫描原子预扣
       +------------------------------------+
       | Redis reserved_count 原子增加 2     |
       +------------------------------------+
                  |
                  v 步骤 2: 数据库落盘生成待支付订单 (Status: UNPAID)
       +------------------------------------+
       | MySQL: insert into reservations    |
       | 状态: UNPAID, expire_at: NOW + 15m |
       +------------------------------------+
                  |
                  v 步骤 3: 向延迟消息队列投递 15 分钟定时检测消息
       +------------------------------------+
       | RocketMQ / Kafka 延时 Topic        |
       | (Payload: reservation_id: 10086)   |
       +------------------------------------+
                 /                                 \
(场景 A: 用户在 15m 内完成支付)          (场景 B: 用户超时未支付 / 放弃)
               /                                     \
              v                                       v
   【支付成功驱动确认】                      【延时队列消费者触发超时关单】
   1. 订单状态更新为 CONFIRMED               1. 检查订单状态是否依然为 UNPAID
   2. 异步将实际扣减持久化至 DB              2. 状态原子翻转为 CANCELLED_EXPIRED
   3. 释放 Redis 预留占用 (保持永久扣减)     3. 执行库存补偿 (Compensation):
                                               - Redis: HINCRBY reserved -2
                                               - 房间瞬时重新释放，供他人预订！
```

### 5.1 严禁轮询数据库：延时消息队列与时间轮（Hashed Wheel Timer）

很多初级工程师习惯使用 Spring Scheduled 或 Linux Crontab 定时器，每隔 1 分钟跑一次扫表 SQL：
`SELECT * FROM reservations WHERE status = 'UNPAID' AND expire_at <= NOW()`。

**为什么必须严厉禁止定时扫表？**
1. **数据库磁盘 I/O 周期性尖刺**：每次扫表都会触发对状态字段的范围索引扫描，在数百万活跃订单的表中，CPU 和磁盘 I/O 每隔一分钟就会出现一次严重抖动。
2. **精度极差**：如果用户在第 0 秒下单，定时任务在第 14 分 59 秒刚跑完，那么这个订单实际上在第 15 分 59 秒才会被关闭，整整白白锁定了房间近 1 分钟，极大降低热点房间的流转周转率。

**工业级解法：精准延时队列（Delay Queue）**  
- **RocketMQ 延时等级 / 任意精度延时消息**：在下单事务提交后，立即向 RocketMQ 发送一条带有 15 分钟延时属性的消息。
- **时间轮算法（Hashed Wheel Timer）**：在高性能网关或内存服务中，利用环形数组加双向链表维护微秒级的高效内存定时器，时间复杂度为 $\mathcal{O}(1)$，到期瞬间精准触发超时事件。

## 6. 五星级酒店“超订（Overbooking）”的物理与业务建模

在酒店业和航空业中，旅客因突发行程变更有相当高的比例（通常为 5%~15%）临时取消订单（Cancellation）或直接缺席（No-Show）。为了避免房间空置造成巨大的固定成本浪费，**超订是一项合法的核心业务需求**。

```
[动态超订限额计算模型]

  物理实际房间数 (Capacity) = 100 间
            +
  动态超订弹性空间 (Overbooking Buffer) = 10 间
  (由历史 No-Show 概率、淡旺季、用户信用等级动态综合计算)
            |
            v
  最大对外可销售房间上限 (Sales Ceiling) = 110 间
```

### 6.1 架构层如何防止“超订失控”？
1. **动态分层阈值**：
   - 并非所有房型都允许超订。普通标准大床房（可替代性极强）允许 10% 超订；而总统套房、独栋别墅（全酒店仅 1 套，不可替代）的 `overbooking_limit` 强制写死为 `0`。
2. **免费升级（Complimentary Upgrade）容灾机制**：
   - 当实际到店人数超过物理大床房容量时，系统自动触发升档规则，**免费将超出的旅客升级到豪华套房**。因此，底层的可用性判定必须支持**跨房型级联兜底计算**。

## 8. 总结：系统设计面试交付范式

在面试中拆解“高并发酒店与票务预订系统”时，应当按照清晰的递进脉络展现资深工程师的专业度：

   - 明确指出酒店预订与普通电商的本质区别在于**连续日期矢量库存的原子约束（All-or-Nothing across Date Range）**。
2. **用数学思维消灭死锁**：
   - 援引 Dijkstra 1965 年死锁破坏公理，清晰指出交叉预订会导致循环等待死锁，确立**“锁定前必须对日期按物理升序强制排序”**的铁律。
3. **推导高并发 Redis Lua 工业级落地**：
   - 彻底分析悲观锁的连接池雪崩与乐观锁的高冲突重试代价，给出**基于 Redis Lua 脚本“第一遍 Dry-Run 预检 + 第二遍原子扣减”的两遍扫描方案**，将 50,000 QPS 并发锁定在微秒级完成。
4. **两阶段生命周期与延时闭环**：
   - 彻底摒弃高成本的定时轮询扫库，设计**精准延时消息队列 / 时间轮驱动的 15 分钟超时关单补偿机制**，并给出五星级酒店受控超订与跨房型免费升级的业务容错方案。
