**TL;DR：** "HTTP/2 解决了队头阻塞"是个流行误读。准确说法是：HTTP/2 消灭了 **应用层 HOL**（一个响应没写完不挡其他响应），但 **TCP 传输层的 HOL 原样保留**——同一个连接上所有逻辑流共用一条字节流，任一包丢失，重传期间整个连接停滞（典型 1 RTT）。RFC 9113 引言明说"TCP 队头阻塞不被本协议解决"。另外 HTTP/2 的流控参数放大了慢流问题：**每个流初始窗口只有 65,535 字节**，一个大响应写满窗口后，该流会被流控卡住，而其他流又会被 TCP 连接级调度拖累。判断"要不要换 HTTP/3"的关键指标是丢包率，不是并发请求数。

## 一、直觉错在哪：把"多路复用"当成"无阻塞"

HTTP/2 把请求/响应拆成帧，按流（stream）交错放在一条 TCP 连接上。这确实解决了 HTTP/1.1 的问题：连接被大响应占住时，后到的请求只能排队（"应用层 HOL"）。但"一个流不挡另一个流"只在**应用层话语权内成立**：

```
TCP 连接 = 一个有序字节队列
  ├── stream 1 的 DATA 帧（大响应，慢速写）
  ├── stream 2 的 HEADERS 帧 ← 想快，但排在 stream 1 的字节后面
  └── stream 3 的 DATA 帧
```

TCP 对应用层暴露的永远是一段顺序字节流：接收方必须按序组装，一旦序号有洞（丢包），**洞后面的所有字节——不管属于哪个流——都要等重传填上**。这就是传输层 HOL。HTTP 层再"多路"，排队的还是同一根管子。

注意一个细节：这里有两层账。**调度账**（谁的帧先发）由 HTTP/2 框架在应用层写；**输送账**（哪个包先到达）由 TCP 重传引擎写。后者才是 HOL 的宿主。

## 二、两个 HOL 的会计科目：应用层（已解决）与传输层（未解决）

| 层 | 谁写的调度 | 阻塞条件 | HTTP/2 状态 | QUIC 状态 |
| --- | --- | --- | --- | --- |
| 应用层 | HTTP 实现 | 响应未写完挡住新请求 | **已解决**（stream 交错） | 已解决（同） |
| 传输层 | TCP 重传 | 丢包时字节流排洞 | **未解决**（RFC 9113 §1 自认） | **已解决**（包独立序） |

传输层 HOL 的代价用一个例子看真切：同一连接 20 个流并发，丢 1 个包。所有 20 个流的头部总量可能只有几百字节，但**全部 20 个流都要等 1 个 RTT**（重传 + ACK 往返），哪怕洞只遮 1 个流的一帧。这是乘法账：丢包率 × 并发流数 × RTT。

## 三、流控窗口：65,535 字节的隐性排队税

RFC 9113 规定：每个新流和整个连接的接收窗口初值**都是 65,535 字节**。窗口用完了流就停，等 WINDOW_UPDATE。

这个数字的两个后果：

1. **大流被窗口饿死**：64KB 的一次普通响应就能打穿流窗口。等窗口恢复，排队从"字节流"转成"信用"，不等也得等。接收方何时回 WINDOW_UPDATE 全由实现决定（RFC 只约束语义，不约束策略）。
2. **连接级窗口共享**：65535 是整个连接里所有流共用的池子（可调，但初始值就是这样）。慢速流（读得慢）会悄悄把池子吸干，让快流也卡在"连接窗口不足"。这也是很多人体感"HTTP/2 在弱网下反而慢"的直接账：TCP 保序 + 连接级窗口 = 双重排队。

> 细节：只有 DATA 帧吃窗口（RFC 9113 §5.2.1 第 5 条），HEADERS/SETTINGS 等控制帧不占用——所以"头部被挡"很少，真正被挡的是大块 body 数据。

## 四、什么时候 HOL 真的痛：三种现实

| 场景 | 丢包率 | 症状 | 值得换 HTTP/3？ |
| --- | --- | --- | --- |
| 机房内/云内 RPC | <0.01% | 几乎无感 | 不必，收益 <1% |
| 公网 API（4G/5G 弱网） | 0.1-1% | 单连接并发多了就卡 | 值得，每 RTT 都是全连接陪 |
| 大文件/视频流 | 丢包高峰 | 缓冲反复打转 | 值得，流控隔离 |

判断标准**不是**并发数，而是**链路丢包率**：HTTP/2 的 HOL 惩罚只在丢包时发生。丢包为 0 时 HTTP/2 比 HTTP/1.1 好一个数量级；丢包 1% 时反而不如多连接 HTTP/1.1——这就是 QUIC 的登场理由（连接迁移 + 包级独立，见[QUIC 连接迁移](/writing/quic-http3-connection-migration)）。

## 五、可复现实验（Linux 一条命令）

用 `tc netem` 给回环加 1% 丢包，对比 HTTP/2（单连接）与 HTTP/1.1（多连接）：

```bash
# 服务端：node 或 nginx 启用 HTTP/2；客户端并发 50 个资源
curl --http2 --parallel -o /dev/null "http://127.0.0.1:8080/{1..50}.js"
curl --http1.1 --parallel -o /dev/null "http://127.0.0.1:8080/{1..50}.js"
# 注入丢包
sudo tc qdisc add dev lo root netem loss 1%
# 重跑上面两条，对比 time_total，然后移除
sudo tc qdisc del dev lo root
```

我在 macOS 上无法注入环回丢包（`netem` 只在 Linux 内核），所以没贴数字——用上面命令在本机复现。注意结果解读：**无丢包时 HTTP/2 胜（多请求复用一条连接），丢 1% 时并发优势被 HOL 稀释**。

## 六、本机（macOS）能做的无丢包对照

- 用 curl 观察 HTTP/2 交错：`curl --http2 --trace-ascii - https://example.com` 看同一个连接里多个流的帧。
- 用 Chrome DevTools Network 面板"协议"列确认握手是否走 h2。
- 双环境对比：把同一批静态资源放到 HTTP/1.1 服务器（没有 ALPN 提示、迫降 http/1）与 h2，看 `navigator.connection.effectiveType` 弱网模拟下的慢资源时间。

## 七、结论

HTTP/2 的队头阻塞账本分两栏：**应用层已清账**（流交错）、**TCP 层原封不动**（字节序）。叠加 65,535B 初始流控窗口与连接级窗口共享，HTTP/2 "解决 HOL"的说法只在无丢包的顺滑网络上成立。丢包率是唯一的判定指标：

- 丢包 ~0（机房内）：HTTP/2 是最优单连接方案，别折腾。
- 丢包可见（移动弱网、出海链路）：落单一次就是 1 RTT × 全连接，回退 HTTP/1.1 或上 QUIC。

| | 应用层 HOL | 传输层 HOL | 流控窗口 |
| --- | --- | --- | --- |
| HTTP/1.1 | ✗（无多路） | —（每请求一连接） | — |
| HTTP/2 | ✓ 解决 | ✗ 保留 | 65,535B/流+连接 |
| HTTP/3 | ✓ 解决 | ✓ 隔离 | 每流独立 |
